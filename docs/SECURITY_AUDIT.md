# Inbox Nudge security audit and release status

Reviewed 2026-11-06 (Pacific time); machine-readable evidence is timestamped 2026-11-07 UTC. Extension version: **0.2.2**.

This is a local code/dependency review and remediation, not an independent penetration test, Google-approved assessment or promise that no vulnerabilities remain. **Public release is blocked** until hosting, real-provider validation, privacy operations and Google/Chrome approvals are complete. No Store item has been submitted, no backend has been deployed publicly, and no real email or device alert was sent during this review.

## Scope and evidence

Reviewed Manifest V3 permissions/CSP, Gmail content-to-background messages, app credential storage/rotation/sign-out, OAuth state/nonce/PKCE and identity verification, metadata ownership/recipient checks, email idempotency, push endpoints, API inputs/request abuse, production configuration, packaging and container contents. Actual Google/notification delivery is mocked in automated tests.

Additional hardening: API validation responses no longer echo rejected credential-bearing input; JWT signing secrets are masked and database connection strings excluded from configuration representations/serialization; optional Web Push no longer follows redirects beyond the approved-host boundary; the archive builder rejects symlinks and excludes source/secrets/backups/unrelated workers. The existing Gmail runtime-invalidation cleanup remains covered by a real Chrome Reload-button regression.

Bandit’s six B105 matches are two comparisons that explicitly reject the known public demo secret, three standard `token_type: bearer` protocol strings, and Google’s public OAuth token endpoint URL. These are not live embedded passwords. The raw findings have not been suppressed or silently converted into a clean scan.

## Controls reviewed without a confirmed bypass

OAuth uses an exact return allowlist, one-time handoff, state, nonce, server-side PKCE, signature/issuer/audience checks and mailbox identity verification. App JWT algorithms are fixed; extension token families are checked server-side, rotate and expire, and are revoked on replay/sign-out/disconnect. Google credentials stay encrypted on the backend. Both Chrome storage areas restrict access to trusted extension contexts. Content messages require the owning extension, Gmail top-level frame, mailbox identity, and server-created tab/account-bound tickets.

Mailbox IDs are actor-scoped; recipients are independently matched by original Message-ID. Database queries use ORM/bound parameters. UI inserts text instead of untrusted HTML, and opt-out HTML escapes names. Fixed Google HTTP requests verify TLS and do not follow redirects. Email submission crosses a durable send boundary once; unknown outcomes are reconciled without automatic resending. These observations describe the inspected code, not a proof that all combinations are safe.

## Remaining blockers and limits

1. **Hosting:** no public backend/domain/database is selected. Provision HTTPS and managed PostgreSQL with validated certificate chains, storage/backup encryption, secret-manager access controls, fresh production secrets/data and backups that have been restored in a test. Do not upload the developer SQLite database or its backups.
2. **Operational abuse protection:** set trusted proxies and transport/edge timeouts correctly. Database counters are shared by design, but distributed-IP flooding, slow clients and volumetric DDoS still need hosting-edge controls. Limits can affect users sharing a NAT; validate expected usage before launch.
3. **Real runtime validation:** complete consenting two-account Gmail/Chrome testing. Tests use synthetic Gmail DOM/provider responses and mocked outgoing delivery. Run PostgreSQL concurrency/worker tests against the actual candidate and scan the final container/OS/runtime. Docker’s daemon was unavailable for a runtime image build in this workspace.
4. **Privacy and deletion:** publish an accurate operator-approved policy, homepage and support contact. Implement/test retention, verified deletion, shared-record handling, suppression records and backup expiry. Disconnect removes credentials, not all metadata/history; there is currently no complete self-service account-erasure feature. Drafts are not publishable policies.
5. **Google:** `gmail.readonly` is restricted and the backend processes restricted Gmail-derived metadata. Public use requires applicable restricted-scope verification and, unless an exception applies, an annual approved third-party security assessment. This review does not replace it. [Google scope definitions](https://developers.google.com/workspace/gmail/api/auth/scopes), [verification/assessment requirements](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification).
6. **Chrome:** register the developer account, reserve the draft item ID, use the exact production ZIP, supply truthful privacy/permission disclosures and final screenshots, and pass Store review. Do not publish the localhost ZIP or claim guaranteed delivery, universal custom notifications, end-to-end encrypted metadata, or a completed independent certification. [Store publishing](https://developer.chrome.com/docs/webstore/publish).

Proceed using [the release guide](CHROME_RELEASE.md). The backend remains behind the scenes; users can continue working entirely through the extension and Gmail.
